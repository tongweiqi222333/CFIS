# Phase 6 混合负载与资源验收

日期：2026-11-01，Asia/Shanghai。实际独立测试，所有请求访问真实API。

## 环境和负载

Docker Desktop / WSL，12个逻辑CPU、约15.5GiB内存；PostgreSQL 18.6，256MB共享内存；grafana/k6:1.4.0，API以cfis_app受限角色运行。初始数据为10万目标交易、10万背景交易、10万已过账凭证和20万分录，均为明确标识的合成数据。

持续300秒、8VU：4VU同一账户收入并立即重试；2VU同一应收单结算并立即重试；1VU创建非资金手工凭证并过账、重复过账；1VU同时查询报表、导出Excel并检查试算平衡。金额使用字符串0.0001，唯一请求编号和凭证编号重试检查贯穿全程。

## 资源与正确性

实际42次资源采样，包含每次采集耗时，约7秒一条。API内存66.34–232.8MiB，最后154.9MiB；数据库356.9–493.7MiB，最后490MiB。目标库连接数2–11，采样最大同时锁等待6个。同账户竞争与企业凭证排他锁产生等待，未发生HTTP错误；不能把这些短时样本作为无内存泄漏证明。

原始脱敏指标见 performance/phase-6-results.json，资源样本见 performance/phase-6-resources.jsonl。k6汇总中的scenarios对象未保留配置，实际4/2/1/1VU配置以performance/mixed.js及本报告为准。

测试后的SQL重算账户余额、结算范围、冲销关系、预算行、凭证平衡、期间及来源金额/币种/日期；唯一约束和逐次重试断言验证无重复入账。临时容器和数据库已由脚本清理。

## 失败与修复记录

首轮120秒混合负载通过。一次300秒运行与生产切换重叠，数据库被主动重启，188项检查失败；该轮不作为最终验收。此后独立300秒请求全部通过，但新增来源恢复校验使用UNION+CASE连接而执行过慢。将其改为三种来源各自按企业和来源编号连接，先在同一数据集校验通过，再从空临时库完整重跑300秒，最终脚本退出0。没有降低阈值或删除失败日志。

## 复现与限制

    docker compose build api
    ./scripts/test-performance.ps1 -Mixed -Duration 300s

运行期间不要切换Compose生产配置或重启PostgreSQL；勿连接真实生产库。脚本保存含测试凭据的context/runtime.env到被忽略的performance/results，不得作为报告上传。

本次验证同账户收入、应收结算、手工凭证及Excel混合负载；不代表所有写入类型、公网容量、数日稳定性或生产SLA。读查询索引前后对比沿用Phase5报告；当前继续no-store，不增加缓存。
