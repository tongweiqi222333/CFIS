# CFIS 部署、升级与恢复手册

## 本地验证和发布

开发环境依照 README 启动。每次代码更新后先备份，执行 `scripts/migrate.ps1`，再构建并重启 API。迁移账户与运行账户分离，迁移后必须重新授予运行角色权限。`/health/ready` 同时验证数据库连接和不存在待执行迁移；`/health/live` 只验证进程存活。

```powershell
./scripts/backup.ps1
./scripts/migrate.ps1
docker compose up -d --build api
./scripts/test-upgrade.ps1
./scripts/test-browser.ps1
```

正式发布前通过后端全量测试、前端构建、浏览器四条流程、依赖扫描及恢复演练。GitHub Actions 使用独立 PostgreSQL，执行构建、迁移、测试及真实 Chromium。测试、压力和恢复工具仅连接本机随机临时库，不允许将这些脚本用于生产数据库压测。

## HTTPS 与 Production 模式

```powershell
./scripts/init-deployment.ps1
docker compose -f compose.yaml -f compose.production.yaml config --quiet
docker compose -f compose.yaml -f compose.production.yaml up -d --build
```

访问 `https://localhost:8443`。初始化脚本生成的是本地自签名演练证书，浏览器会提示不受信任；真实公网部署需提供域名及可信 TLS 证书，并按实际网络调整监听地址。不得把测试跳过证书检查的方式用于真实客户端。`test-release.ps1` 自动完成本地 Production 演练，然后返回开发配置，不删除数据卷。

Production 关闭自主注册，只通过管理员邀请加入。首次部署先在受控本地环境创建 Owner，随后关闭注册。`compose.production.yaml` 隐藏数据库及 API 的宿主端口，仅通过 HTTPS 前端代理访问。未配置跨域访问；浏览器同源调用 API。凭据只保存在浏览器内存，不写入本地持久化存储。

Production 使用单独的 `production_keys` 卷，并用 `output/deployment/protection.pfx` 加密新保护密钥；密码来自 `.env` 的 `PROTECTION_CERTIFICATE_PASSWORD`。开发与生产演练密钥隔离，切换环境后需要重新登录。真实环境升级必须保留原密钥、加密证书和应用名 CFIS，保证历史访问及刷新凭据可解密。

## 身份与邮件

`Auth:AllowRegistration` 在开发默认开启、生产默认关闭。`GET /api/v1/auth/options` 提供注册和密码找回可用状态。邀请令牌有效48小时，数据库只存 SHA-256 摘要；一次使用后失效。新用户在接受邀请时设置密码，已有用户必须使用受邀邮箱登录。邀请人若已被移除或失去相应管理权限，邀请不能接受。邀请不会自动发送给他人，由管理员通过可信渠道交付。

角色更新和移除每次请求立即按数据库成员关系生效，不影响该用户其他企业的合法成员身份；Owner 不可由这些接口降权或移除。密码重置和全局退出使旧安全戳失效。公共登录和找回入口不因浏览器携带旧令牌而被阻挡；刷新入口仍由 Identity 校验刷新令牌与安全戳。

在 `.env` 配置以下生产邮件参数，重建 API 容器使其生效：

```text
SMTP_HOST=your-smtp-host
SMTP_PORT=587
SMTP_FROM=your-sender-address
SMTP_USER=your-smtp-user
SMTP_PASSWORD=your-smtp-secret
```

发送器默认要求 STARTTLS。本地测试通过配置 `Smtp:EnableSsl=false` 使用隔离 SMTP 接收器，验证实际协议投递；密码重置流程另用测试专用接收器验证安全戳和代码单次有效。未配置 SMTP 时密码找回统一返回503，界面明确失败；不会返回或记录重置代码。自主注册不强制邮箱确认；需要强制确认的部署应先配置邮件并单独验收注册策略。

## 会计启用和业务验收

本版本采用完整历史接入策略，不跳过启用日期前的业务。打开会计引擎，检查最早业务日期、尚未覆盖期间的流水、未映射账户、未入账资金和未确认应收应付。从最早业务日期起补齐期间及映射，逐页生成草稿并过账。已有期初流水只导入一次，不另建同金额期初凭证；来源唯一约束和重试逻辑防止重复导入。跨历史范围可建立多个不重叠期间。

批量操作每批最多50项，每项独立事务，返回成功、编号和失败原因；成功项不会因其他项失败回滚。修正缺少映射或错误期间后可重试，已成功来源或已过账凭证保持幂等。失败请求不应更换业务含义后沿用原请求编号。

结账前使用预检查及阻塞明细页面，处理未入账来源、未映射账户和草稿；对账差异到试算与资金对账表定位，再从来源编号追溯凭证及科目明细。正式结账会重新取得企业锁并检查，不依赖之前的页面检查结果。数据库再次保护历史来源完整性、有效单据确认、来源金额/币种/日期、借贷平衡及资金与总账一致。

业务验收覆盖应收和应付确认、分两次结算、部分撤销、再次结算、超额拒绝、全部撤销、确认冲销、单据取消、试算对账和结账。现金报表统计收付款，权责发生制试算收入费用统计会计确认；尚未收款的销售可增加会计收入，但不会增加现金。取消单据与退款、冲销必须按各自步骤办理，历史记录不被覆盖。

## 备份与灾难恢复

`backup.ps1` 生成数据库 dump、开发环境保护密钥 tar、配置 env，若已有保护 PFX 则一并复制；这些文件均在被 Git 忽略的 backups 目录。备份中包含密码和身份密钥，归档后需加密离线保管并限制访问。生产保护卷须从当前 Production 配置导出，不能误用开发密钥卷；同时保存 PFX、密码及历史证书。附件上传模块未在本版本实现，没有附件文件可备份；将来启用时必须同步纳入文件清单和一致性验证。

`verify-restore.ps1` 随机恢复临时库，检查交易、余额、往来、预算、会计及身份数据；摘要v5额外包含邀请记录。旧摘要格式只执行一致性检查，不冒称与新摘要可直接比较。

`test-disaster-recovery.ps1` 先写入明确标识的合成用户和财务数据，再备份；在新容器、新随机数据库和新密钥卷中恢复。验证恢复前密码、访问令牌、刷新令牌、精确金额及恢复后收入办理。应用使用 `cfis_app`，结束后删除临时容器、临时数据库和临时密钥卷，保留备份与脱敏结果。

本地演练实际耗时见 `recovery-phase-6-results.json`。这不是生产恢复承诺。当前为快照备份，没有配置 WAL 连续归档/PITR，快照之后的业务不在备份中。实际最大丢失范围由备份间隔决定；备份频率、保留期限及异地存储需按企业要求配置。

真实恢复顺序：停止业务写入；保存事故现场；建立隔离环境；恢复与备份匹配的程序、数据库、配置、保护密钥及证书；执行一致性和登录检查；如需升级先在副本演练；确认业务与报表后切换入口。不得将恢复脚本的临时库清理命令改为主库名称。

## 升级失败与回退

`test-upgrade.ps1` 从 Phase5 第10条迁移建立独立基线，写入标识数据，升级到当前12条迁移，核对原有账户摘要、不存在模型变更及财务一致性。正式执行前保存应用版本、镜像标识、迁移列表和备份时间。

本阶段新增邀请表和触发器，未批量改写历史金额。应用回退仅能使用与当前数据库结构兼容的旧版本。数据库回退应恢复升级前备份到隔离库验证后切换；不能假定执行 Down 可保留新增邀请或升级后发生的业务。恢复旧备份会失去快照后的写入，必须先停止写入并明确处理差额。

## 日常检查

监控就绪状态、HTTP错误率、响应时间、磁盘、数据库连接及锁等待、备份成功和恢复演练时间。查看 `docker compose logs --tail 100 api`，使用错误响应 traceId 定位；不记录密码、令牌或重置代码。报表和受保护API统一 no-store；导出仍进行企业权限验证。

五分钟混合负载及资源采样见 `performance-phase-6.md`。短时本地测试不证明数日内无内存泄漏，也不构成公网并发 SLA。未引入 Redis、消息队列或微服务。

## 失败测试后的本地清理

初始化失败可能使xUnit跳过正常释放。确认没有测试仍在运行后执行 ./scripts/clean-test-databases.ps1。脚本仅枚举本地Compose内匹配 cfis_(test|e2e|perf|restore)_加32位随机十六进制后缀且无活动连接的数据库，逐项再次校验名称，不使用强制断开；主库cfis永不匹配。本次已实际清理38个失败初始化遗留库，复核临时库为0。
